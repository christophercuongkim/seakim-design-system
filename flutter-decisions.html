QUESTION 1

Custom widgets, or themed Material?

Flutter ships Material Design as its default widget set. You can restyle it heavily, but some of its shape and behaviour is baked into the widgets themselves. The question is whether you fight that or skip it.

Option A · themed Material

Configure ThemeData, use Material widgets

You write a ThemeData that maps SeaKim tokens onto Material's slots, then use FilledButton, Card, NavigationBar and friends. 

// theme mapped from SeaKim tokens
ThemeData(
  colorScheme: ColorScheme.dark(
    primary: tokens.fillAccent,
    surface: tokens.surfaceCard,
  ),
  filledButtonTheme: FilledButtonThemeData(
    style: FilledButton.styleFrom(
      shape: RoundedRectangleBorder(
        borderRadius: BorderRadius.zero,
      ),
      minimumSize: const Size(0, 34),
    ),
  ),
)

// then, everywhere
FilledButton(onPressed: …, child: Text('Book trip'))
Roughly what Material gives you by default:
  • Much less code. Maybe 800 lines total instead of 4,000.
  • Free accessibility and platform behaviour — semantics, focus traversal, keyboard shortcuts, desktop scrollbars, text selection, right-click menus.
  • Free updates. Flutter improves Material every release.
  • Material's ink ripple fights your motion rules. Your system says press = 0.97 scale at 80ms; Material says expanding ink splash. Removing the ripple properly is fiddly.
  • Elevation is Material's organising idea, and "borders define, shadows lift" is yours. You'd be suppressing elevation in a lot of places.
  • Density and sizing constantly drift back to Material's 40/48px minimums against your 28/34/42.
Option B · custom widgets — my recommendation

Build SeaKim widgets on Flutter primitives

You skip Material's widget layer and compose from Container, InkWell-free GestureDetector, Focus, AnimatedScale — the same primitives Material itself is built on. 

// widget owns the system's rules directly
class SkButton extends StatefulWidget {
  // … variant, size, iconLeft, loading
}

// build():
AnimatedScale(
  scale: _pressed ? t.pressScale : 1.0,   // 0.97
  duration: t.durInstant,                 // 80ms
  child: DecoratedBox(
    decoration: BoxDecoration(
      color: t.fillAccent,
      border: Border.all(color: t.borderDefault, width: 1),
      // no borderRadius. no boxShadow.
    ),
    child: …,
  ),
)

// then, everywhere
SkButton(onPressed: …, child: Text('Book trip'))
What your system actually specifies:
  • Exact fidelity. Square corners, hairline borders, 34px controls, scale-press, no ripple — because nothing else is in the widget.
  • Your rules are enforced by the API, not by remembering to override. There is no radius parameter to misuse.
  • One mental model with the web kit. SkButton takes the same props as Button.jsx.
  • You own accessibility. I'd add Semantics, Focus, and keyboard handling per widget — real work, and easy to under-do.
  • ~4× the code, and it's yours to maintain forever.
  • Desktop niceties you'd rebuild: hover cursors, scrollbar styling, tooltip timing, text field context menus.
Why I lean B for you: your system's three loudest decisions — 0px radius everywhere, shadows only on floating things, and springy scale-press — are exactly the three Material resists hardest. Under Option A you'd spend the saved code on override plumbing, and the result would still read slightly Material. That said, a hybrid is legitimate and might be the real answer: custom widgets for everything visual, but keep Material's TextField, Scrollbar, and route/dialog machinery underneath, since those carry the most invisible platform behaviour and the least SeaKim styling. QUESTION 2

Where the Dart lives

You said let's talk it through. Three shapes, and the trade is between convenience now and versioning later.

Shape What it looks like When it's right
1. Folder in here
simplest		 
seakim/
  styles.css
  components/
  flutter/
    lib/
      seakim.dart
      tokens/
      widgets/
    pubspec.yaml
 The web and Flutter sides stay in one place, so a token change is one commit and reviewers see both. Good while the system is young and both sides are moving. Downside: your Flutter apps can't depend on it cleanly — they'd use a path or git dependency pointing into a subfolder.
2. Standalone pub package
most correct		 
seakim_flutter/
  lib/
    seakim_flutter.dart
    src/tokens/
    src/widgets/
  assets/fonts/
  pubspec.yaml
  CHANGELOG.md
 A real package your apps add as a versioned dependency — private git or a hosted pub server. Voyage can pin 1.2.0 while Bench is still on 1.1.0, which matters the moment two apps ship on different schedules. Downside: tokens now live in two repos, so they can drift.
3. Package here + generated tokens
what I'd do		 
seakim/
  tokens/*.css      ← source of truth
  flutter/
    tool/gen_tokens.dart
    lib/src/tokens.g.dart  generated
    lib/src/widgets/       handwritten
    pubspec.yaml
 Package-shaped so apps can depend on it properly, but the colour and spacing values are generated from your CSS rather than retyped. The CSS stays the single source of truth; drift becomes impossible instead of merely discouraged. Widgets are handwritten. Downside: one small generator script to maintain.
The reason I favour 3: your accent system is computed — oklch(0.72 0.13 H) with H rotating per app. Dart can't evaluate that, so every ramp step has to be baked to sRGB. Retyping ~50 colour values per app by hand is where a design system quietly dies. Generating them means adding app four is still "pick a hue, run the script."
